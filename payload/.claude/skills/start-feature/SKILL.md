---
name: start-feature
description: Run one slice end to end from a thin orchestration context — merge gate, branch, plan (forked, best model), implementers in sequence (agents, each proving its task), reviewers and the full check in parallel (agents, a `sonnet` subagent), reading (`Explore`, `haiku`), triage, delivery, PR — relaying the four stops to the user. Use to start every slice, in a fresh session (the project's settings start it on `opus` at `high` effort); holds the loop and the model table, the single source CLAUDE.md points to.
argument-hint: <NN> <short slice name>
disable-model-invocation: true
---

Slice to run: $ARGUMENTS. Effort of this session: `${CLAUDE_EFFORT}` — the orchestrator runs at `high` (the table below; `.claude/settings.json` sets it): a lower value means a `--effort` flag or a `/effort` choice overrode it, so say so to the user before the merge gate and go on only on their word (the model is checked by a hook before this prompt reaches you; when the hook could only note that it did not know the model — after `/clear`, or in a headless session whose model comes from a settings file — compare your own model with the table and treat a mismatch the same way). You are the **orchestrator**: you dispatch, read reports, decide, and talk to the user. You never run the app driver, a build, the full check suite or a long tool loop yourself, and you never read a diff, a file or a log longer than a screen — a forked skill or a subagent does, and returns a report; a read that only has to locate or extract (where is X, what does this log say, which lines of this diff touch Y) goes to `Explore`. Keep this context thin: it is the one re-sent at every turn.

Models and effort — this table is the single source; the skills and agents carry theirs in their frontmatter, `/start-feature` itself runs on the mid model, `opus` at `high` effort, which `.claude/settings.json` sets as the project's defaults (`model`, `modelSettings`). `best` is Claude Code's alias for `fable` where the account has it, else `opus`; it is documented for skills, not for agents, so `security-reviewer` names `fable` (replace by `opus` if the account has no Fable). Opus 5.5, Sonnet 5.5 and Haiku 5.5 default to `medium` effort in Claude Code: the agents that must not skip a file or a test run carry a higher one. `haiku` (Haiku 5.5) only reads: it locates and reports, and what it reports is re-checked at the source before anyone acts on it; never `haiku` for anything that judges, writes or runs code. `Explore` is the project's own agent (`.claude/agents/Explore.md`): it replaces the built-in one, which runs on the caller's model. Claude Code re-runs a request flagged as cybersecurity on Opus 4.8 when the model is Fable 5.1, Fable 5 or Opus 5.5 (flagged as biology: on Opus 5), so the `security-reviewer` can run in part on Opus 4.8; `/usage` shows the models a slice really used.

| --------------------------------------------------------- | ------------ | -------------------------------------------- | -------- |
| `/start-feature` (this context)                           | session      | `opus` (project default)                     | `high`   |

What a forked skill or an agent reports is a lead, not a fact: anything you repeat to the user or act on (a number, a path, a verdict) you have read in its report with the evidence next to it. A forked skill cannot talk to the user: its questions come back in its report, you ask (`AskUserQuestion`, recommended option first) and send the answers back to the same agent (`SendMessage`).

0. **Merge gate.** `gh pr list --state open`: an open PR of a previous slice means stop and tell the user — nothing starts before it is merged (`gh pr view <N> --json state` → `MERGED`; local-only project: the user's word). Then `git switch main && git pull`, and branch `feat/<NN>-<kebab-name>` from it.
1. **Plan.** Invoke `/plan-feature <NN> <name>`: it runs in its own context on the best model and returns the plan path, the loop size, its open questions and what it decided alone. Relay the questions to the user (`AskUserQuestion`, recommended option first); send the answers back to the same planner agent (`SendMessage`) until the plan is final and committed. **Stop 1**: present the plan summary and wait for the user's approval. Nothing else runs while you wait: no code, no test, no probe, no change to a tracked file — the plan itself read the installed versions it depends on, and the first implementer finds out whether the environment runs.
2. **Build.** For each task of the plan, in order, **one `implementer` agent at a time**, on the slice branch, with the task text, the plan path and whether the task is a load-bearing artifact — the agent carries `/tdd`, its model and its effort. No worktree unless the user asks for parallel tasks on this slice: then the independent tasks go one agent each, dispatched in the same message with `isolation: worktree` (the worktree branches from the slice — `worktree.baseRef` is `head` in `.claude/settings.json`); each report names its branch and worktree, which you merge into the slice branch with `git merge --no-ff`, then remove (`git worktree remove <path>`, `git branch -D <branch>`): a worktree is a full checkout with its dependencies, and Claude Code removes it on its own only when the agent changed nothing; dispatch them without a `name` and resume them by the ID their dispatch returned — where agent teams are enabled (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`), a named agent starts as a teammate, and a teammate gets no worktree. On an implementer's report, chain the next task at once: the end-of-task notification may not wake you, and there is nothing to verify between two implementers (each one's gate ran). Never end a turn on "waiting" when the next step is decided. A plan that flags a load-bearing artifact: the agent builds and returns the artifact alone first; **Stop 2**: present it, wait for validation, then resume the same agent (`SendMessage`) with the verdict.
3. **Review and check, in parallel, in one message.** Dispatch `slice-reviewer`, and `security-reviewer` on `Loop: full` and whenever the diff touches authentication, authorization, the session or state that outlives a screen or a request (steps 1–2 of `/review-diff`: range command, untracked files, plan path, nothing else); and a `sonnet` subagent that runs the project's **full check once** — typecheck, lint, the whole test suite, what the CI checks (`CLAUDE.md` "Commands") — with its output redirected to a file, and reports the decisive lines; they go in the PR. It is the only full run of the slice before the CI: each task was proven by its implementer (the tests covering its change through its stop hook, its e2e spec played by name, the screen or the output looked at), so no e2e suite runs here — the CI plays it on the PR where the project has one. Anything red in the check is a finding of step 4.
4. **Triage.** Steps 4–6 of `/review-diff`, in this context: confirm each finding against the code (read the lines, delegate a reproduction when it is not a one-liner), sort it — apply (`implementer` agent, test first: its gate proves the tests covering the fix), **Stop 3** (changes scope, a recorded decision, visible behaviour, a load-bearing artifact, or unconfirmed: present with a recommendation and wait), or optional. A fix of more than a few lines is reviewed by a fresh-context reviewer. **A red test is red: zero replays.** A flaky test met on the way is fixed or skipped in this slice (the stack's skip marker, with the number of the issue opened for it), never re-run to see.
5. **Deliver.** A cheap-model subagent puts each thing where `CLAUDE.md` "Where things are written" says: it rewrites the current-state documents the slice changed (`README.md`, the slice's line of the milestone path in `SCOPE_PLAN.md`, `docs/<topic>.md`, `CLAUDE.md` where the plan asks) and deletes what is no longer true; appends the user's decisions of this slice to `docs/decisions.md` under the next numbers; opens an issue for each follow-up, spec gap or action for the user the slice found (`gh issue create --label …`); writes the log entries if the project keeps a log; and drafts the PR body from `.github/pull_request_template.md` (review findings and their outcome, `Closes #N`, the issues it opened, the evidence read in the implementers' reports and in the check output). The reviewers' memory, written during steps 3 and 4 (`.claude/agent-memory/`, tracked by git), goes in the slice's last commit: nothing else includes it. You read it, push, open the PR. At once, and after every later push to the PR, start a **CI watcher** in the background (Bash `run_in_background`) where the project has a CI, after a `sleep 15` so the run of that push is registered (else it reads the previous run): `gh pr checks <N> --watch --fail-fast --interval 60 > <scratchpad>/ci-watch.log 2>&1; echo "exit=$?"` — it wakes you when it exits; the user never has to tell you the state of the CI. Green: say so. Red: download the log of the failed job into a file (`gh run view <run> --job <job> --log-failed`; `Explore` has no network, it reads the file), tell the user, and treat it as a finding of step 4 — confirmed, fixed test-first by an `implementer`, pushed, watcher restarted; **Stop 3** when it changes scope or visible behaviour; never a replay to see. **Stop 4**: the merge is the user's. Start nothing for the next slice.

Proportionality: a one-sentence diff (typo, rename, log line, dependency bump) skips 1, 2 and the reviewers — branch, change, the tests covering the change (the command of `.claude/hooks/gate-tests.cmd`), PR. Tests follow the diff: the tests covering the change for a task and for a fix; the full check once per slice, by the subagent of step 3, then the CI.
